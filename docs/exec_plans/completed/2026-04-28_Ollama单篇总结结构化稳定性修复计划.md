# 计划：2026-04-28_Ollama单篇总结结构化稳定性修复

## 目的 / 大图景
- 修复本地 Ollama 生成周报单篇总结时大量返回无效 JSON 的问题。
- 让本地模型输出链路可诊断、可恢复、可稳定产出，而不是只靠“跳过失败项”掩盖问题。
- 保持周报任务不会无限消耗本地计算资源，并保留失败证据用于后续调参。

## 背景与定位
- 2026-04-28 用户在 UI 中使用 `ollama_api / gemma4:26b` 生成周报。
- 当前状态显示 `summary_completed=8/27`，其中 `summary_skipped=3`，只有少数单篇总结成功写出。
- 最近失败从超时转为 `Unterminated string...`，说明 Ollama 返回的 `message.content` 不是完整 JSON。
- 现有代码只把坏 JSON 转为未完成项，但没有解决本地结构化输出不稳定的根因，也没有保存原始坏输出。

## 工作范围
- Ollama API 结构化调用方式。
- 本地模型输出的 JSON 提取、修复和失败落盘。
- 单篇总结失败诊断与测试。
- UI/状态保持现有跳过逻辑，不扩大周报内容风格改动。

## 非目标
- 不重新生成整份周报。
- 不删除输出目录中已有总结。
- 不调整标签体系和周报推荐规则。

- [x] 步骤 2：修复 Ollama JSON 解析与失败落盘
- [x] 步骤 3：补充稳定性测试
- [x] 步骤 4：验证并重启 UI

## 计划中的工作
- 先用当前配置做一个最小 Ollama 结构化请求，确认坏 JSON 是否来自模型输出而非 UI。
- 将 Ollama 返回内容保存到诊断日志，避免下次只能看到 JSONDecodeError。
- 对模型常见输出形态增加安全提取与一次轻量修复，不盲目接受非 schema 内容。
- 保留“修复失败则跳过并列入未完成项”的保护。

## 具体步骤
1. 检查当前 Ollama 请求 payload、schema 和失败输出位置。
2. 修改 `llm_api_support.py`，增加 JSON fenced block 提取、简单截断修复和失败诊断落盘所需字段。
3. 修改 `llm.py`，为 Ollama 调用传入 request name 并把无效输出写到 `log/llm_tmp`。
4. 增加测试覆盖 fenced JSON、截断 JSON、失败落盘和周报跳过。
5. 运行针对性测试、全量测试、`harness-check`，最后重启 UI。

## 发现与意外
- 最小复现显示，`gemma4:26b` 在 Ollama `format: json_schema` 下会返回被截断的 JSON，例如 `tags` 数组字符串未闭合。
- 同一模型在普通 chat 模式下能正常生成中文总结；问题集中在 schema/json format 约束模式。
- 修复后用真实失败文章“Comprehensive and Open Assessment of Thermospheric Models...”做本地请求，已能返回合法 JSON。

## 决策记录
- 不把无效 JSON 直接视为成功；只有能解析成对象并通过后续字段访问的内容才进入缓存和输出。
- 本轮只做低风险修复，不引入新的重试 LLM 调用，避免本地模型卡住时重复消耗。
- Ollama 本地模型不再直接使用 `format: json_schema`；改为普通 chat 请求追加 JSON 字段契约，然后由本地解析器校验 required 字段。

## 结果与复盘
- Ollama 单篇总结结构化调用已改为本地兼容模式，避免 schema mode 截断 JSON。
- 增加了 fenced JSON 提取、required 字段检查和坏输出诊断落盘。
- 如果本地模型仍返回无法解析的内容，该篇仍会被记录为未完成并跳过，不会终止整份周报。
