# 计划：2026-04-11_tag治理工作流重构

## 目的 / 大图景
- 把当前混乱的“正式 tag / 候选 tag / 审阅报告”工作流重构成一套稳定、可人工接管、可被 harness 审核的标签治理流程。
- 明确 source of truth：正式 tag 由人工可读的 Markdown 文件主导，机器 JSON 只是运行时镜像；预选 tag 在人工核准前绝不进入正式体系。
- 给 UI 增加“标签管理”入口，把查看正式 tag、查看预选 tag、预选转正这三件事收口到设置页中。
- 让预选 tag 自带真实使用频次，便于人工按“是否真的被输出使用”来筛选。

## 背景与定位
- 当前正式标签主要由 `config/focus_tags.json` 驱动，候选标签原始记录落在 `data/tag_candidates.json`，审阅报告默认写到 `log/tag_candidates_review.md`。
- 现状问题：
  - source of truth 不清晰：人工文件、运行时 JSON、日志报告三套并存；
  - 候选 tag 的可视化形式偏“审阅报告”，不是稳定的工作台；
  - UI 没有标签治理入口；
  - harness 只检查 `focus_tags.json` 结构，不检查正式/预选的一致性和转正闭环。
- 目前候选 tag 也没有和真实输出库建立稳定连接，人工无法直接看到某个 tag 到底在多少篇文章总结或多少份深度解读里出现过。
- 用户已给出新的治理规则，要求把“正式”和“预选”两条链路彻底拆清。

- 本轮不处理“哪些 tag 本身合理”的内容校准，只先把治理流程和人工入口搭起来。

## 计划中的工作
- 先把“正式 tag”和“预选 tag”的 source of truth 分离成固定文件。
- 再定义 Markdown 与 JSON 的同步方向，确保人工编辑优先。
- 然后给设置页加“标签管理”子面板和三个操作按钮。
- 最后把 doctor / harness / UI review 一起补齐，避免流程再次漂移。

## 具体步骤
1. 确认新文件布局：
   - 正式 Markdown：`config/tag/formal_tags.md`
   - 预选 Markdown：`config/tag/pending_tags.md`
   - 正式机器 JSON：`config/focus_tags.json`
   - 预选机器 JSON：`config/pending_tags.json`
2. 定义同步规则：
   - 正式 tag：`formal_tags.md` 为人工 source of truth；如人工修改，程序同步生成 `focus_tags.json`。
   - 预选 tag：运行时新增 tag 只进入 `pending_tags.json`，并同步渲染到 `pending_tags.md`；绝不直接进入正式体系。
   - 转正动作：只读取 `pending_tags.md` 中被勾选的 tag，写入 `formal_tags.md`，再由正式 Markdown 回写 `focus_tags.json`。
   - 转正完成后，被接收的 tag 必须从 `pending_tags.md` 和 `pending_tags.json` 中剔除，避免重复待审。
3. 定义 Markdown 结构：
   - 正式 tag：按层级树展示，适合人工维护和审阅。
   - 预选 tag：按层级树展示，并带复选框；勾选表示“允许转正”。
   - 预选 tag 的每个 tag 后显示真实使用次数，统计来源仅限真实输出库中已存在的文章总结和深度解读文件。
4. 定义 UI 改造：
   - 在“设置”页新增“标签管理”子面板。
   - 新增三个按钮：`显示正式tag`、`显示预选tag`、`tag转正`。
   - “显示”行为以打开对应 Markdown 文件为准；“转正”执行同步和校验流程。
5. 定义 harness：
   - doctor：检查正式/预选 Markdown 与 JSON 是否存在且结构可解析。
   - harness：检查正式 Markdown 与 `focus_tags.json` 是否一致；检查预选中已勾选但未转正、已转正但未清理、未收录新 tag 漏写入预选等漂移问题。
   - harness：检查预选 tag 的次数统计是否可由真实输出库中的文章总结与深度解读文件重新计算得到。
   - UI functional/visual：检查设置页出现“标签管理”子面板和 3 个按钮，并验证按钮对应行为。
6. 定义迁移：
   - 从当前 `config/focus_tags.json` 生成初始 `config/tag/formal_tags.md`。
   - 从当前 `data/tag_candidates.json` 迁移到 `config/pending_tags.json`，并生成 `config/tag/pending_tags.md`。
   - 迁移完成后，原 `log/tag_candidates_review.md` 和 `data/tag_candidates.json` 退出主工作流。

## 发现与意外
- 当前 `tag_candidates_review.md` 并不是稳定文件，而是运行时报告；它不适合作为人工长期维护入口。
- 现有 `focus_tags.json` 同时承担了 canonical tag 词表和运行策略配置（如 `candidate_log_path`）；如果正式 Markdown 变成 source of truth，需要谨慎处理“词表内容”和“运行规则配置”的边界。
- 标签治理检查如果先“自动纠偏”再“做检查”，会把真实漂移吞掉；因此单独拆出了只读的 `tag_governance_review.py`，供 harness 判断 formal/pending 是否失配。
- 预选 tag 的 Markdown 必须保留全部未转正 tag，不能像旧“候选报告”那样按阈值裁切；CLI 的 `--min-count` / `--limit` 只影响终端打印，不影响预选文件本身。

## 决策记录
- 采用“两套 Markdown、两套 JSON”的治理结构，而不是继续把预选放在日志目录。
- 正式 tag 的人工 source of truth 固定为 Markdown，不再让日志报告或运行时候选文件承担正式治理职责。
- 预选 tag 在未人工核准前绝不进入正式 tag，这是硬约束，后续要在 harness 中明文检查。
- UI 的“tag转正”只做转正和同步，不做内容推断，避免 UI 入口再次变成黑盒自动改词表。
- 预选 tag 的次数统计只认真实输出库中的文章总结和深度解读文件，不统计缓存、日志、评测产物或临时文件。
- 预选 tag 的次数按“真实输出文件中出现的次数”计算；由于单个 tag 在单个输出文件中通常只出现一次，实际效果接近“被多少篇文章总结/深度解读使用”。

## 结果与复盘
- 已完成的实现：
  - 新建 `config/tag/formal_tags.md`、`config/tag/pending_tags.md`、`config/pending_tags.json`，并把正式 / 预选 tag 工作流固定下来。
  - `focus_tags.json` 改为保留机器规则和正式词表镜像，`pending_tags.json` 改为保留运行期未转正 tag。
  - 文章总结、深度解读、CLI、UI 设置页和 doctor 已全部接到新工作流。
  - harness 新增 `tag_governance_review`，并把设置页“标签管理”入口纳入 functional / visual review。
- 这轮保留的边界：
  - `formal_tags.md` 只接管正式 canonical tag 集合，不直接覆盖 JSON 里的 `aliases`、`patterns`、`suppression_rules` 和其他机器规则。
  - 预选 tag 的次数只统计真实输出库中的文章总结和深度解读，不统计缓存、日志或评测产物。
- 后续真正要继续做的是“内容层面的 tag 语义校准”，不是继续重构治理骨架。
