# 计划：2026-04-30_UI批量深度解读运行监控与修复

## 目的 / 大图景
- 监控 UI 文件夹批量深度解读功能的真实运行，记录多篇 PDF 的排队、逐篇生成、失败恢复和输出落盘行为。
- 等所有文章生成或任务结束后，系统性审计批量深读输出质量，归纳程序和算法层面的缺陷。
- 基于真实问题修正深度解读程序、tag 审核、Markdown 后处理或批量任务状态逻辑，而不是只手工修几篇输出文件。

## 背景与定位
- 单篇 UI 深读已连续暴露并修复元数据、revision 字段别名、tag 根类和 Markdown 格式问题。
- 用户现在要测试文件夹内多篇文章的批量深度解读，需要验证批量链路是否继承这些修复，并检查多篇运行时是否有新的状态、缓存或失败处理问题。
- 当前 `/ui-status` 暂未显示新批量任务，仍停留在上一篇 Buynovskiy 的完成状态；本计划先进入守候和监控。

- 不只修正生成出来的几篇 Markdown；输出重写只能作为验证和收敛步骤，核心要修程序或审核算法。

## 决策记录
- 本轮先观察真实批量运行，不提前做大范围重构。
- 批量输出问题优先在通用深读链路解决，避免每篇输出单独打补丁。
- 对前三篇的“关系等级裸输出”不降级校验标准，而是在 Markdown 后处理层补上保守解释，并同步收紧 Ollama final/revision prompt，避免缓存或新输出再次卡死。
- 对第四篇的 evidence JSON 失败，优先增强 Ollama structured-output 修复能力和 evidence prompt 的 JSON 约束，而不是跳过 evidence 阶段。
- tag 修复采用通用深读审核层的短语归一与证据门槛：实体/仪器/模型归根，不把坏 tag 只在生成文件里替换。

## 结果与复盘
- 监控到 UI 批量深读真实运行 4 篇 PDF，首轮 UI 结果为成功 0、失败 4。前三篇失败于 Markdown 本地校验的“与已有工作的关系”裸等级输出，第四篇失败于 Ollama evidence JSON 字段名前缺双引号。
- 修复 Ollama JSON 修复候选，支持 `_open_questions"` 这类字段名前缺双引号的输出；同步强化 evidence prompt 的 JSON 字段名约束。
- 修复深读 Markdown 后处理，使 `直接相关/间接相关/弱相关/不相关` 带句号时也会扩展成保守解释，不再被校验挡住。
- 批量任务逐篇失败时现在会在 progress payload 中记录当前失败 message、`last_failed_pdf` 和 `last_failure_message`，便于 UI/监控定位。
