# 计划：2026-04-09 UI 细化第四轮

## 目的 / 大图景
- 把 `config-ui` 从“能用的配置表单”继续收紧成“真实控制面”。
- 让 UI 展示、底层运行逻辑、人工中转工作流和维护 gate 保持一致，避免 UI 看起来能配、程序实际不按这个逻辑执行。
- 把这轮细节优化沉淀成可持续维护的实现，而不是一次性的页面修补。

## 背景与定位
- 当前 `config-ui` 已完成左侧导航和右侧工作区的重构，但仍存在页面布局、最新结果展示、设置项分层和运行逻辑不一致的问题。
- 用户已明确指出：这轮不只是调样式，还要收口实际配置逻辑，尤其是 provider、LLM 运行方式、周报设置和人工中转的职责边界。
- 这轮完成后，UI 应更接近“面向使用者的操作面板”，而不是“开发者内部参数堆叠页”。

## 计划中的工作
- 先做 UI 信息架构收口，明确每个页面到底承担什么功能。
- 再做 Markdown 结果渲染，让“最新结果”真正能在 UI 中阅读。
- 随后收口设置页和底层运行配置逻辑，避免保留无效或误导性参数。
- 最后回到样式细节、滚动与面板高度对齐，并通过测试和维护 gate 验证。

## 具体步骤
1. 检查当前 `config-ui` 的页面分区和保存逻辑，列出与用户要求冲突的项。
2. 为“最新结果”引入统一 Markdown 渲染层，避免周报、深读、人工中转各自重复实现。
3. 调整总览、周报、深度解读、人工中转四个页面的版面结构和滚动行为。
4. 重构设置页，把“周报运行参数”“provider 选择”“本机私有输出路径”等逻辑重新归类。
5. 清理 `llm.py` 与 UI 强绑定的旧参数，确认默认运行逻辑只依赖真实需要的配置项。
6. 补测试，验证 UI 输出、表单保存、manual import、provider 逻辑和维护 gate。
7. 回填本计划中的发现、决策和结果，再移动到 `completed/`。

## 发现与意外
- 单靠 `PLANS.md` 文字说明不足以稳定计划输出；如果没有程序校验，计划结构会在多轮任务后逐渐漂移。
- 直接把新的计划模板强制套用到所有 `completed/` 历史计划上，会立刻把旧归档变成发版阻塞项。这不适合作为当前 gate。
- UI 中“看起来能配”的很多项，底层其实已经不该再作为默认运行逻辑依赖，尤其是 LLM enable 开关、数量限制和深读输入字符上限。
- 项目 `.venv` 里没有现成的 Markdown 渲染库，UI 最新结果展示不能依赖额外包，必须提供本地可回退的渲染实现。

## 决策记录
- 本轮计划使用中文记录，后续新计划默认沿用中文标题与内容。
- “最新结果”在 UI 中应显示渲染后的 Markdown，而不是只给文件路径。
- 人工中转页不应暴露项目内部 `request_id` 作为主要用户信息。
- 设置页必须反映真实运行逻辑，不能继续保留“看起来能配、实际上不会生效”的开关和阈值。
- `ExecPlan` 监督模块只强制模板文件和 `active/` 中的计划；`completed/` 暂按历史归档处理，不把旧格式直接纳入阻塞 gate。
- 周报功能不再通过隐藏的“启用/关闭”开关控制；当前 UI 和运行逻辑都按“手动可执行”处理。
- `chatgpt_web_manual` 保留为底层 provider，但不再作为设置页的全局分析后端选项；进入“人工中转”页面时按任务自动使用。
- UI 最新结果渲染采用项目内置的轻量 Markdown 渲染器，并兼容 Obsidian wikilink 的基础转换。

## 结果与复盘
- 已新增 `exec_plan_review` 监督模块、`docs/exec_plans/TEMPLATE.md` 模板和配套测试，把计划结构稳定性正式接入 `harness-check`。
- UI 已完成这轮核心收口：
  - 总览只保留运行统计、交互日志、运行环境、LLM 状态。
  - 周报、深度解读、人工中转页面都能直接渲染最新 Markdown 结果。
  - 周报期刊列表改成按逻辑分组的纯文本滚动面板。
  - 深度解读和人工中转首行面板高度对齐。
  - 设置页合并成“分析后端 + 私有输出路径”两块，不再暴露无效参数。
- 底层逻辑已同步收口：
  - UI 不再保存 LLM enable 开关、数量限制、深读输入字符上限。
  - 周报每日运行支持显式 `hydrate` 参数。
  - `llm.py` 不再依赖这些已移除的旧 UI 配置项。
- 本轮 gate 全通过，说明这次不仅页面变化完成，而且 harness 和维护逻辑也没有被带坏。
- 后续如果再继续做 UI，建议单独开新计划，不再把这轮继续叠加。
