# Source of Truth Governance Phase 2

## Purpose / Big Picture

第二阶段专门治理 `ScienceMonitor` 的控制面漂移问题：

- 模板写了一套
- 提示词写了一套
- 规则文档写了一套
- Python 真正执行的又是另一套

这一阶段先不重写生成逻辑，而是先把“谁说了算”写清楚，并把修改规范接入根级入口文档。

## Surprises & Discoveries

- 单篇总结模板最初虽然被读取，但并不参与真实 Markdown 结构渲染
- 周报模板目前没有被程序直接消费，正式结构完全由 `reporting.py` 控制
- 深度解读的真正结构最初同时受 `llm.py` 的 schema 与 `deep_reads.py` 的渲染/校验控制，展示层模板并未进入真实链路
- 把模板真正接入渲染链路后，最关键的不是“怎么替换字符串”，而是要保留旧解析函数依赖的区块契约和输出校验

## Decision Log

- 第二阶段先从“代码主控、文档明确参考位阶”起步，再逐步把适合的展示层迁到运行时模板
- 只有在测试护栏和模板契约都到位后，才允许模板进入真实渲染链路
- 后续每处理一个漂移点，都要先声明该面向的主 source of truth
- 单篇总结采用“模板主控展示层 + 代码主控字段内容与契约”的折中方案，不把全部业务逻辑塞进模板
- 深度解读也采用“模板主控展示层 + 代码主控 schema、字段归一化与输出校验”的折中方案
- 一旦模板进入真实运行链路，就优先归到 `config/`，而不是继续留在 `docs/`
- 研究偏好这类“机器要读、但人会频繁改”的内容，优先采用“Markdown 编辑入口 + JSON 落地文件”的双层方案

## Context and Orientation

- 当前最关键的新文档是 `docs/workflow_specs/source_of_truth_matrix.md`
- 它描述的是“修改顺序”和“优先级”，不是新的业务需求
- 后续真正开始改模板或代码时，应以这份矩阵作为第一检查表

## Plan of Work

1. 先固定控制面矩阵
2. 再挑选一个最典型的漂移面向开始治理
3. 每治理一处，就同步补测试或校验护栏
4. 避免一次同时重写模板、提示词和渲染代码

## Concrete Steps

1. 生成链路改动前，先确认属于“研究偏好 / 结构 / 提示词 / 标签 / 验收”中的哪一类
2. 如果 source of truth 发生变化，同步更新矩阵、入口文档和 ExecPlan
3. 先处理高收益、低风险的漂移项，再进入模板驱动化或大文件拆分
4. 下一步优先评估提示词、规则文档和模板之间是否还存在新的漂移点
