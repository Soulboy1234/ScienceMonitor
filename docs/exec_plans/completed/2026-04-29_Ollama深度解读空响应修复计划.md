# 计划：2026-04-29_Ollama深度解读空响应修复

## 目的 / 大图景
- 修复 UI 深度解读使用 `ollama_api` 时出现的 “Ollama response did not include structured text content”。
- 保留深度解读必须看全文的原则，同时降低 Ollama 最终报告阶段的空响应和截断风险。
- 增强 harness：Ollama 空响应必须留存原始返回，便于定位本地模型、上下文、输出长度或接口结构问题。

## 背景与定位
- 本次报错发生在 Ollama 深度解读流程。
- 日志显示第一阶段 `deep_read_evidence_*` 已成功，并记录了 token 使用。
- 报错发生在第二阶段最终深度解读，当前代码没有保存空响应的原始 JSON。

## 计划中的工作
- 让 Ollama 空响应进入统一的 provider invalid-output 路径，写入 `log/llm_tmp/*_invalid_output.txt`。
- 格式化 evidence payload 时兼容数组，避免把数组写成 Python repr。
- Ollama 深度解读质量模式改成：第一阶段读取全文，第二阶段使用全文证据提纲和压缩后的全文核对材料生成最终报告。
- 用测试确认单篇摘要总结不受影响。

## 具体步骤
1. 修改 Ollama 结构化调用，空 `message.content` 时把完整响应 JSON 写入错误对象。
2. 修改深读 evidence 格式化，兼容 string/list。
3. 为 Ollama 深读最终阶段引入全文核对材料压缩，证据阶段仍使用全文。
4. 补充单元测试。
5. 运行 targeted tests、全量测试、`git diff --check`、`harness-check`。

## 发现与意外
- 第一阶段证据预分析已经成功，说明 Ollama 服务本身可用。
- 现有错误没有记录原始响应，这不符合 harness 可诊断性要求。
- `keep_alive=0` 对单篇总结有利于释放资源，但深度解读两阶段之间可能导致模型卸载后第二阶段空响应。

## 决策记录
- 深度解读“看全文”的责任由第一阶段证据预分析承担，第二阶段可以使用证据提纲加压缩核对材料生成报告，避免重复把完整正文送入本地模型造成空响应。
- 当请求名以 `deep_read` 开头且用户配置 `keep_alive=0` 时，程序临时使用 `deep_read_stage_keep_alive=1m`；这不会改变文章总结的逐篇释放策略。

## 结果与复盘
- Ollama 空响应现在会进入统一的 `AnalysisProviderInvalidOutput` 路径，并把原始响应写入 `log/llm_tmp/*_invalid_output.txt`。
- 深度解读请求在 `keep_alive=0` 时会临时使用 `deep_read_stage_keep_alive=1m`，避免两阶段之间卸载模型造成空响应；单篇总结仍按用户配置逐篇释放。
- Ollama 深度解读质量模式第一阶段读取全文，第二阶段使用证据提纲加压缩核对材料生成最终报告，以降低本地模型空响应和 JSON 截断风险。
- Evidence payload 现在兼容数组，避免把数组渲染成 Python 列表字符串。
