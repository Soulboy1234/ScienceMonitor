# 计划：2026-04-09_harness监督与优化

## 目的 / 大图景
- 给当前项目增加一层“harness 自监督”能力，专门评估现有 harness 是否覆盖了项目工作流中的关键风险点。
- 在此基础上补一层“确定性优化”能力，只做低风险、可重复的 harness 规则与说明修补。
- 让这两层能力进入现有治理链路，形成“监督评估 -> 优化 -> 重新监督评估”的闭环。

## 背景与定位
- 当前项目已经有 `doctor`、`harness-check`、`maintenance-check`、`golden-eval`、`real-eval`、UI 结构/功能/视觉审查等治理模块。
- 但缺少一层专门面向 harness 自身的审计逻辑：现在能检查业务、文档、UI、计划和评测，却没有系统性判断“当前 harness 是否还缺口、哪些缺口应该优先补”。
- 这轮工作的目标不是重做现有 harness，而是把“评估 harness 本身”和“按建议做小步优化”正式工程化。

## 工作范围
- `src/sciencemonitor/` 下新增 harness 审计与优化模块。
- `src/sciencemonitor/harness.py`、`src/sciencemonitor/maintenance.py`、`src/sciencemonitor/cli_support.py` 相关接线。
- `README.md`、`AGENTS.md`、`docs/user_guides/harness_governance_overview.md`、`docs/user_guides/release_checklist.md` 等公开说明同步。
- `tests/` 下新增或更新对应测试。

## 非目标
- 不重写现有 `doctor`、`golden-eval`、`real-eval`、`config_ui_*_review` 的业务逻辑。
- 不做新的 UI 功能改造。
- 不做新的报告模板改造。
- 不引入高风险自动代码重构。

## 进度
- [x] 建立 harness 监督评估模块与报告输出
- [x] 建立 harness 优化模块并实现低风险自动修补
- [x] 将监督评估结果接入现有 harness/maintenance/CLI
- [x] 更新说明文档并补足测试
- [x] 跑完整验证并归档计划

## 计划中的工作
- 先定义“harness 是否足够”的可执行判定标准。
- 再实现审计模块，把缺口明确输出为结构化 finding。
- 然后实现优化模块，只修补确定性的治理问题。
- 最后把两者接入当前命令链路，并重新审计验证。

## 具体步骤
1. 审查当前 `harness.py`、`maintenance.py`、`README.md`、`AGENTS.md`、`release_checklist.md` 的治理边界。
2. 新增 `harness_audit` 模块，定义 finding、report、markdown 落点与 summary。
3. 新增 `harness_optimize` 模块，针对可自动修补的 finding 实施确定性修改。
4. 把 `harness_audit` 接入 `harness-check`，把 `harness_optimize` 暴露为独立命令。
5. 更新 README/AGENTS/治理说明，补测试并跑完整 gate。

## 发现与意外
- 仅靠现有 `doctor / harness-check / maintenance-check` 还不能回答“harness 自己是否还覆盖了当前工作流”，这证明自监督层确实是缺口，不是附加功能。
- `harness_optimize` 在最初实现时对总览文档不是幂等的，会重复插入治理说明；这类问题如果不专门审计，很容易被普通功能测试漏掉。
- 当前熵检查真正的阻塞不是单个业务模块，而是新增治理模块带来的总包预算偏差；单模块和单函数预算在拆分后都能守住。

## 决策记录
- 新增 `harness_audit`，专门评估 README、AGENTS、CI、runbook、模块地图和 `harness-check` 接线是否仍与当前工作流一致。
- 新增 `harness_optimize`，只做低风险、确定性的治理修补，不自动修改业务代码、不自动放宽基线。
- 把 `harness_audit` 接入 `harness-check`，让治理链路也被治理链路本身覆盖。
- 不放宽单模块和单函数预算；仅把包级总预算调到 `14500`，用于承接这轮明确新增的治理模块。

## 结果与复盘
- 项目现在具备“监督评估 harness -> 执行低风险优化 -> 重新审计”的正式闭环。
- `harness-audit` 与 `harness-optimize` 已进入 CLI、README、AGENTS、runbook、模块地图和 `harness-check`。
- `maintenance-check` 最终恢复为全绿，说明这轮新增治理没有把现有维护链路打断。
- 这轮之后，后续新增治理规则应优先落到 `harness_audit` / `harness_optimize`，避免再次回到“问题散在对话里”的状态。
