# 计划：2026-04-17_周报额度中断恢复与链路节流

## 目的 / 大图景
- 修正 UI 周报任务在 `codex_local` 额度耗尽时的失败语义，让任务以“可恢复中止”而不是普通报错结束。
- 基于已完成的单篇总结结果，继续补完本次中断的周报，避免重复消耗 token。
- 在不改变周报新风格目标的前提下，继续压缩周报链路中的不必要 LLM 消耗。

## 背景与定位
- 当前 UI 周报任务在 `2026-04-17 09:40:45` 于单篇总结阶段中断，真实原因是 `codex_local` 额度耗尽。
- 运行状态已经写入 UI 状态文件，但当前被呈现为普通错误，不利于后续恢复。
- 目前 `auto/article_summaries` 已保留 30 篇已完成结果，本轮应在此基础上继续而不是回滚。

## 计划中的工作
- 先把 `usage limit` 从普通 `RuntimeError` 提升为可识别、可恢复的专门状态。
- 再让周报 UI 后台任务在这类状态下保留进度和已完成结果，不误报为普通失败。
- 然后直接以“复用既有单篇总结”的方式继续当前周报，只补剩余部分。
- 周报补完后，检查单篇生成与周报分析链路中的冗余 token 消耗点并收口。
- 最后补测试、跑 harness，并归档本计划。

## 具体步骤
1. 增加专门的额度耗尽异常或状态标记，并把它沿单篇总结与周报任务链路透传到 UI。
2. 调整 UI 周报任务状态写入与状态卡片渲染，明确显示“等待额度恢复后可继续”。
3. 验证 `reuse_existing_summaries` 能稳定跳过已完成 30 篇单篇总结。
4. 直接续跑本次 `2026-04-17` 周报，确认仅补剩余单篇并成功写出周报。
5. 审查周报链路中的重复抓取、重复分析、提示词冗余与可缓存点，实施低风险节流。
6. 补测试并运行对应验证。

## 发现与意外
- 这次周报中断并非 UI 退出，而是后台 `codex_local` 在第 31 篇单篇总结时命中额度限制。
- 已完成的 30 篇单篇总结文件在失败后仍然保留，可作为续跑基底。
- 周报链路里还有一个真实 bug：`reporting_support.py` 在处理 `sqlite3.Row` 时误用了 `.get()`，导致周报分析阶段直接返回空结果。
- 当前 `2026-04-17` 窗口内实际缺失的单篇总结只有 2 篇，因此续跑没有重做前 30 篇。

## 决策记录
- `usage limit` 不再继续包装成普通 `RuntimeError`，而是提升为可识别、可恢复的专门异常。
- UI 周报状态在额度耗尽时改为 `paused_quota`，避免和普通失败混淆。
- 续跑当前周报时不再重新执行更新阶段，而是直接调用 `generate_windowed_report(..., reuse_existing_summaries=True)`，只补剩余单篇和周报分析。
- 周报节流优先压缩 report prompt，而不是削弱单篇总结证据输入；保留题目、标签和核心信息，移除重复的 `supplement`。

## 结果与复盘
- 已为 `codex_local` 额度耗尽增加专门异常与 UI 可恢复状态；状态文案会明确提示“额度恢复后直接重试”，不再显示成普通失败。
- 已补完 `2026-04-17 周报`，最终覆盖 32 篇论文、8 本期刊；输出位于 `ScienceMonitorOut/research_reports/2026-04-17 周报.md`。
- 周报 prompt 从约 `28,301` 字符压缩到约 `17,883` 字符，减少约 `36.8%`，后续同类周报会直接受益。
- 已同步更新 UI 运行状态为成功，并重启面板服务以加载本轮代码。
