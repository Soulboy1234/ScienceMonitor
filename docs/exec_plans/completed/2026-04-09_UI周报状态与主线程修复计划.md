# 计划：2026-04-09_UI周报状态与主线程修复

## 目的 / 大图景
- 修复 `config-ui` 中点击生成周报后在后台线程触发的 `signal only works in main thread of the main interpreter` 异常。
- 为周报页面补上可实时刷新的运行状态面板，让 UI 用户能看到当前步骤、已抓取文章数量、运行时长和可用时的粗略预计时长。
- 把这次修复纳入现有 harness，避免后续再次出现“功能失败但 UI 无状态、测试未覆盖”的回退。

## 背景与定位
- 用户在 `config-ui` 中点击周报生成后，界面没有显示运行状态。
- 实际运行在更新抓取阶段即报错：`signal only works in main thread of the main interpreter`。
- 这次问题涉及 `http.py` 的超时实现、`config-ui` 的同步执行方式、`pipeline.py` 的进度暴露方式，以及 UI 页面渲染与轮询逻辑。

## 工作范围
- `src/sciencemonitor/http.py`
- `src/sciencemonitor/pipeline.py`
- `src/sciencemonitor/config_ui.py`
- `src/sciencemonitor/config_ui_actions.py`
- `src/sciencemonitor/config_ui_support.py`
- `src/sciencemonitor/config_ui_page_sections.py`
- `src/sciencemonitor/ui_assets/config_ui.js`
- 相关测试与试验记录

## 非目标
- 不重做整套 UI 视觉风格。
- 不改动周报内容生成逻辑本身。
- 不引入新的长期后台任务系统；仅实现当前 `config-ui` 的单任务周报状态跟踪。

- [x] 步骤 1：定位上次 UI 周报失败点与未生成文章总结的原因
- [x] 步骤 2：修复后台线程中的 `signal` 异常
- [x] 步骤 3：接入周报异步执行与运行状态文件
- [x] 步骤 4：在周报页面渲染并轮询实时状态
- [x] 步骤 5：补测试、更新试验记录并通过 harness

## 计划中的工作
- 先修底层 `signal` 使用边界，确保后台线程抓取不再直接报错。
- 再把周报执行从同步 POST 改成后台线程任务。
- 通过 `config-ui` 状态文件暴露周报运行状态，并在页面轮询展示。
- 最后补测试、更新运行记录并跑完整 gate。

## 具体步骤
1. 限制 `HTTPClient` 的 signal 超时机制只在主线程启用。
2. 给 `ScienceMonitor.update()` / `run_daily()` 增加可选进度回调。
3. 为 `config-ui` 增加周报任务状态写入、读取与后台线程启动逻辑。
4. 在周报页面的“最新结果”上方增加运行状态卡片，并用前端轮询刷新。
5. 补充测试，验证：
   - 后台线程不再触发 signal 异常
   - 周报状态面板可显示运行中与完成态
   - 现有 harness gate 全绿

## 发现与意外
- 上次 UI 周报没有生成新的文章总结，不是生成步骤失败，而是更新抓取阶段先崩了。
- 现有 `harness` 之前只覆盖了 UI 结构、视觉和部分交互，没有覆盖“长任务执行状态”这条链路。

## 决策记录
- 采用后台线程 + 状态文件 + 轮询，而不是长连接或 WebSocket，优先保持当前本地单机架构简单稳定。
- 预计时间只做粗略估计；如果缺少足够进度信息，则宁可留空也不伪造精确值。
- 状态信息优先复用 `config_ui_state.json`，避免引入第二套 UI 运行态文件。

## 结果与复盘
- `HTTPClient` 现在只在主线程启用 signal 型超时，UI 后台线程不再触发主线程异常。
- `config-ui` 周报生成改成后台线程执行，并通过 `config_ui_state.json` 暴露实时状态。
- 周报页面新增“周报运行状态”面板，可显示当前步骤、已抓取数量、来源进度、运行时长和粗略预计时长。
- 这次补上了 UI 长任务状态这条 harness 缺口；相关逻辑已进入 `pytest`、`harness-check` 和 `maintenance-check`。
