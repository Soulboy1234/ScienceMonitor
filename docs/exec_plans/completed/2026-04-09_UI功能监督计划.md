# 计划：2026-04-09_UI功能监督

## 目的 / 大图景
- 为本地控制台增加一层独立的 UI 功能监督模块，检查页面“能不能用”，而不只是“长得像不像”。
- 把导航切换、滚动复位、provider 切换、关键功能页交互可用性接入 `harness-check`，形成 UI 结构审查、视觉审查、功能审查三层护栏。

## 背景与定位
- 当前已经有 `config_ui_review`（结构）和 `config_ui_visual_review`（布局/视觉）两层检查。
- 但用户现在进入了“逐页试功能”的阶段，需要一层真正模拟交互的监督，避免页面结构和视觉都正常、交互却失效。
- 这层监督属于 harness engineering 的运行质量治理，而不是单纯前端体验优化。

## 计划中的工作
- 用 Playwright 基于 sample rendered HTML 做浏览器交互检查。
- 优先覆盖最容易悄悄坏掉的功能：导航切换、标题更新、滚动复位、provider 面板联动。
- 保持检查轻量，不把它做成完整 UI 自动化测试框架。

## 具体步骤
1. 新增 `config_ui_functional_review.py`，定义 report、issue 和 summary。
2. 在浏览器里模拟点击导航，验证 active view、标题和滚动位置。
3. 模拟切换 provider，验证对应设置面板显隐。
4. 把该检查接入 `harness.py`，让它参与 overall pass/fail。
5. 更新相关测试和文档。
6. 跑 `pytest`、`harness-check`、`git diff --check`，回填并归档计划。

## 发现与意外
- 仅靠结构检查和视觉检查，仍会漏掉“切页后滚动位置是否复位”“provider 面板切换是否真的生效”这类纯交互问题。
- 这类问题不需要完整端到端业务执行，就能在 sample rendered HTML 上通过浏览器交互稳定复现和检查。

## 决策记录
- 新增独立的 `config_ui_functional_review`，专门负责 UI 功能监督，不把它混进结构审查或视觉审查。
- 功能监督先覆盖最核心、最容易回退的交互：导航切换、标题更新、滚动复位、provider 切换。
- 暂不把真实周报生成、真实深度解读执行放进这层检查，避免把 UI 功能监督变成重型端到端测试。

## 结果与复盘
- `harness-check` 现在包含三层 UI gate：结构、功能、视觉。
- 后续如果用户在浏览器里发现“页面能打开但操作不对”的问题，应优先补到 `config_ui_functional_review`，而不是只补静态测试。
- 这层检查保持轻量，适合作为每次 UI 修改后的常规 gate。
