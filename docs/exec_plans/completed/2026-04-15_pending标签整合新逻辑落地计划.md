# 计划：2026-04-15_pending标签整合新逻辑落地

## 目的 / 大图景
- 按《2026-04-15 pending 标签整合方案》把当前 `pending` 从平铺候选池改造成“先归并、后审核、再转正”的治理层。
- 让 `pending` 更接近可审阅的候选家族，而不是历史长尾残留。
- 让标签审核 agent、输出重审流程和 harness 一起遵守同一套整合规则。

## 背景与定位
- 当前 `pending` 仍然按分类平铺展示，虽然已经去掉了 `0次`，但对人工审阅仍然过碎。
- 现有 `tag_review.py` 能把一部分模型标签归并到 formal，但缺少“家族级归并”和“低价值 pending 删除”层。
- 用户已经提供了新的 pending 整合方案，本轮按该方案落地，不额外改动 formal 主干设计。

## 计划中的工作
- 先把新方案拆成可执行规则，而不是直接改 Markdown 展示。
- 再把 pending 生成逻辑改成“先规范化、再聚类、后展示”。
- 然后让审核 agent 和输出重审流程复用同一套规则。
- 最后补 harness gate，确保 pending 漂移、错误前缀和低价值残留能被检查出来。

## 具体步骤
1. 读取方案并抽出程序可执行的家族、归并和删除规则。
2. 修改 pending 刷新逻辑，生成家族化、可审阅的 `pending`。
3. 修改标签审核 agent，使新输出优先落到 formal 风格，无法吸收的再进入 pending。
4. 修改人工备注/转正规则，兼容新 pending 结构。
5. 修改 harness 审核，检查 pending 是否仍残留明显错位和低价值项。
6. 刷新真实 `pending`，运行测试和 `harness-check`。

## 发现与意外
- 当前 `pending` 的核心问题不是数量，而是机器侧缺少“pending 规范化层”。
- 现有 `tag_review` 已能做 formal 归并，但 `pending` 仍直接吃输出标签，导致错前缀和重复簇继续堆积。
- 新方案要求把 `pending` 的展示单位从“分类”切到“审阅家族”，这会同时影响 Markdown 解析、转正动作和 harness 校验。
- 旧实现里 `pending_tags.md` 的人工备注会在刷新时丢失；这轮已把备注和勾选都纳入刷新保留逻辑。

## 决策记录
- 先在 Python 侧实现 pending 家族整合规则，而不是把规则写死在 Markdown 文本处理里。
- `pending` 继续保留 Markdown 作为人工入口，但机器侧 source of truth 仍是 `config/pending_tags.json`。
- `pending_tags.json` 增加家族元数据，Markdown 按家族渲染；分类仍保留给机器判断和后续转正使用。
- 对真实输出库统计时，先做 pending 规范化，再累计使用次数；否则重复簇无法压缩。
- agent 侧不再直接把开放词表结果送进 pending；先走 pending 规范化层，能 formal 化的直接 formal 化，低价值项直接丢弃。

- 已让 `tag_review` 复用 pending 规范化层，新输出会优先并入 formal；无法表达的才进入 pending。
