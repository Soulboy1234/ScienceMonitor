# 计划：2026-04-10_UI周报复用与轮询稳定

## 目的 / 大图景
- 修复 UI 周报页在失败态下持续刷新、无法操作的问题，恢复稳定的人工操作流程。
- 让周报任务对已有单篇总结进行可靠复用，避免同一 DOI 反复生成多个总结文件，降低 token 消耗。
- 增加 UI 可控项，在默认跳过已存在总结的前提下允许显式重做，并把导航栏状态面板布局收稳。

## 背景与定位
- 当前周报任务链路已经能进入单篇总结阶段并上报细粒度状态，但失败态下前端仍会自动 reload，导致页面看起来“卡住”。
- 文章总结目录中存在同一论文多个文件名的重复输出，说明现有复用策略没有完全按 DOI 锁定。
- 用户要求在 UI 周报页加入“跳过已生成总结，除非显式重做”的控制项，并优化左侧导航栏状态卡的锚点布局。

## 计划中的工作
- 先改前端轮询逻辑，确保失败态不会持续 reload。
- 再收紧单篇总结的 DOI 索引、复用和重复文件处理逻辑。
- 然后把周报 UI 的新选项接到底层 `pipeline` 与 `article_summaries`。
- 最后调整导航栏状态卡布局，补测试并跑完整校验。

## 具体步骤
1. 移除或改造周报终态下的自动页面 reload，并让错误状态停留在当前页面。
2. 实现基于 DOI 的既有总结索引，必要时清理同 DOI 的重复自动生成文件，并确保重做时复用同一路径。
3. 在周报参数面板增加显式选项，默认跳过已有总结，取消勾选时强制重做。
4. 调整左侧导航栏运行状态卡和静态信息卡的垂直锚点与间距。
5. 补充定向测试与 UI review，然后跑 `harness-check`、`maintenance-check` 和 `pytest`。

## 发现与意外
- 周报页“卡住”的直接原因不是后台任务仍在运行，而是前端在终态时持续 `reload`，每次重新载入后又再次命中相同终态，形成刷新循环。
- 单篇总结目录中的重复文件不一定来自本轮重跑；更大的根因是旧逻辑只在生成前复用 DOI 命中的文件，但没有在索引阶段主动收敛同 DOI 的历史重复文件。
- 当前 UI 视觉/功能 harness 可以覆盖布局和交互，但不会自动发现“终态 reload 语义不合理”这种策略问题，仍需要结合实际工作流审视。

## 决策记录
- 周报终态下不再自动刷新页面；状态卡停留在成功或失败信息，由用户决定是否手动刷新查看最新结果。
- 单篇总结复用以 DOI 为主键；如果同 DOI 已存在多个输出文件，索引阶段保留最新文件并清理其余重复文件。
- 周报 UI 默认开启“跳过已生成总结”，只有用户显式取消勾选时才强制重做单篇总结。
- 强制重做时仍复用已存在 DOI 对应的输出路径，避免同一篇文章因为重做产生新的文件名。

## 结果与复盘
- 周报失败态不会再触发页面无限刷新，页面可停留在错误状态供人工查看。
- 周报任务现在可以在默认复用既有单篇总结的模式下运行，减少重复 LLM 调用和 token 消耗。
- 单篇总结输出目录对 DOI 的约束更强，未来同一篇论文不应再持续累积多个文件名版本。
- 这轮修改同时触及前端、周报参数传递和摘要输出路径，已经补充到测试与 harness；后续主要风险点转为真实 UI 手测，而不是明显的结构性遗漏。
- 本轮最终通过了定向测试、`harness-check`、`entropy-check` 和 `maintenance-check`，可交由用户重新从 UI 手动发起周报验证真实路径。
