# 计划：2026-04-09_周报报错排查与状态增强

## 目的 / 大图景
- 修复 UI 发起的周报任务在后台执行时报错的问题，恢复周报更新、单篇总结和周报渲染链路。
- 把周报运行状态增强到可操作级别：不仅显示阶段，还显示单篇总结总数、完成数、模型、推理强度和平均 token。
- 将新的状态展示和错误修复纳入现有 harness，避免后续回退。

## 背景与定位
- 用户通过 UI 触发周报任务后，任务在“更新抓取”与“单篇总结”阶段先后暴露出多个问题。
- 已确认当前没有正在运行的周报任务，UI 状态中记录的是失败后的旧状态。
- 当前还缺少对“周报生成到单篇总结阶段的细粒度进度”和“单篇总结 token 平均消耗”的展示。

## 计划中的工作
- 先把已暴露的类型兼容问题收口，确保调试链路可重复执行。
- 再对周报日期窗口内的文章逐篇定位，找出触发 URL 错误的具体记录和代码路径。
- 修复后补充周报运行态统计，并把这些字段展示到 UI 中。
- 最后统一跑 harness、maintenance 和测试。

## 具体步骤
1. 修复 `sqlite3.Row` 在周报/评测链路里的 `.get()` 误用。
2. 用当前周报日期窗口逐篇复现单篇总结，确认哪一篇触发 URL 错误。
3. 修复真实报错根因，并复跑周报更新与生成。
4. 在周报进度回调中加入单篇总结总数、完成数和 LLM 统计。
5. 更新 UI 结果卡片与前端轮询显示。
6. 重启 UI 服务，确认旧导航栏任务与本计划都可归档。

## 发现与意外
- 旧的 `8766` UI 实例残留了过期状态，和主实例 `8765` 显示了不同错误，容易误导排查。
- 周报线程先后暴露出两类独立问题：UI 进度回调签名不兼容，以及单篇总结阶段对网页全文抓取异常缺少降级。
- `sqlite3.Row` 与 `dict` 的混用不只出现在周报链路，也影响真实案例评测与复用逻辑。
- 当前真正阻塞 `maintenance-check` 的只剩包级总行数预算，功能链路与针对性测试已经恢复通过。

## 决策记录
- 周报生成过程中，单篇总结来源解析失败时不再中断整批任务，而是回退到数据库已存摘要继续生成。
- 周报运行状态继续沿用 `progress_callback`，不再额外引入第二套 UI 专用状态通道。
- 平均单篇 token 先按 `codex_local` 的 stderr 日志增量估算；其他 provider 只展示模型与后端，不伪造 token。
- 在真正手动复跑前，先清掉旧 UI 实例并保留一个干净服务，避免把陈旧错误当成新问题。

## 结果与复盘
- 周报状态面板已能展示单篇总结总数、完成数、当前标题、模型、推理强度和平均单篇 token。
- 周报线程的已知崩溃点已经从“进入单篇总结即失败”收敛到“等待用户手动重跑确认”。
- 这轮说明现有 harness 之前更偏向静态检查；针对周报线程和 UI 状态的动态回归，需要继续依赖目标测试与 UI 手测配合。
- 当前 `entropy-check / harness-check / maintenance-check / pytest` 已全部通过，旧周报错误状态将在重启 UI 时清理。
