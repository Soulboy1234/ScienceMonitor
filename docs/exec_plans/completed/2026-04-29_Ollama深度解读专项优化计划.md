# 计划：2026-04-29_Ollama深度解读专项优化

## 目的 / 大图景
- 只优化 `ollama_api` 作为底层 LLM 时的深度解读质量，尽量接近 Codex 深度解读的判断密度和证据分层。
- 明确保护 `codex_local` 深度解读路径：不改 Codex prompt、schema、缓存版本或最终模板。

## 背景与定位
- 当前 Ollama 深度解读已能通过结构校验，但与 Codex 输出相比偏短，关键结果每类通常只有 1 条，局限与证据边界不够清楚。
- 用户已在输出目录保留 `ollama`、`ollama new`、`codex` 三份 Akasofu 样例供对比。
- 本轮属于 Ollama provider 内部质量增强，不改变深度解读 Markdown 展示模板。

## 发现与意外
- Targeted tests 中首次发现质量审计会触发修订；已补足测试 fixture，使“不需要修订”和“需要修订”两种路径分开覆盖。
- Akasofu 真实样例首次运行时，evidence 阶段暴露 Ollama 返回非法 JSON 反斜杠（例如 LaTeX `\epsilon`）的问题；已在 Ollama-only structured output 解析中加入保守修复。
- Akasofu 第二次运行时，模型把 deep-read token 全耗在 `thinking` 字段导致 `message.content` 为空；已仅对 `deep_read*` Ollama 请求默认发送 `think=false`。
- 真实输出还暴露了 Ollama 将 JSON object 字符串原样塞进报告、以及把 `S-M dynamo` 误译成“太阳-月球发电机”的问题；已在 Ollama-only 深读归一化层修复为编号 Markdown 和“太阳风-磁层（S-M）发电机”。
- 最后一轮 `harness-check` 曾因私有输出目录 4 篇单篇总结标签顺序不一致失败；已用项目自带 `reconcile_auto_output_tags_with_review()` 同步标签顺序后通过。

## 决策记录
- Codex 深度解读继续使用现有 `build_deep_read_prompt()`、`build_deep_read_schema()` 和 `deep_read_template_v6`。
- Ollama 深度解读质量模式使用独立 v2 evidence cache，避免复用旧质量模式证据包。
- `ollama_api.deep_read_num_predict` 只覆盖请求名以 `deep_read` 开头的 Ollama 请求；单篇总结、周报、OpenAI、OpenRouter 和 Codex 不受影响。
- 最终 Markdown 模板保持 `config/templates/deep_reading_report_template.md` 不变。

## 结果与复盘
- 已实现 Ollama-only evidence v2 -> richer final context -> 本地审计 -> 条件修订链路。
- Akasofu 样例重新生成成功，输出为私有输出目录中的未加后缀新文件；原有 `- ollama.md`、`- ollama new.md`、`- codex.md` 对比文件未删除或重写。
- 新 Akasofu 输出中关键结果四类均至少 2 条，局限性和人工复核点明确，没有 JSON/list repr，没有无证据“直接相关”，并修复了 `S-M` 误译。
- Codex 路径测试确认不会调用 Ollama-only prompt/schema/revision 逻辑。
