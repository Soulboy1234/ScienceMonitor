# 计划：2026-04-09_v1_2_1备份与v1_3_0大检查

## 目的 / 大图景
- 先把当前累计改动记录为 `v1.2.1`，作为大检查前的稳定备份点。
- 在此基础上对功能、代码、文档和目录进行一次系统性大检查，确认当前项目是否处于可发布状态。
- 仅在功能正确前提下做低风险优化，提升可读性、安全性、稳定性和代码熵控制质量。
- 最终只有在所有 gate 通过时，才记录 `v1.3.0`。

## 背景与定位
- 当前工作树累积了多轮 UI、harness、文档治理和标签参考统一改动，尚未收束成正式版本。
- 项目已经具备 `doctor`、`harness-check`、`maintenance-check`、`golden-eval`、`real-eval`、UI 审查和文档审查等治理能力。
- 这轮的任务不是继续扩新功能，而是把已有改动系统性检查、修正和收口。

## 工作范围
- 当前工作树的版本记录、发布记录和 tag 管理。
- 代码功能、文档准确性、目录摆放、治理链路和 UI 的全量检查。
- 低风险代码优化、熵治理和必要的文档纠偏。
- 最终版本 `v1.3.0` 的记录条件评估与执行。

## 非目标
- 不引入新的大型业务功能。
- 不做历史输出迁移。
- 不做超出当前改动边界的大规模重构。
- 不在检查未完成前提前记录 `v1.3.0`。

## 计划中的工作
- 先确认当前工作树、版本和现有治理状态。
- 再把当前状态收成 `v1.2.1` 备份点。
- 然后并行审查代码功能、文档准确性、文件摆放和熵问题。
- 审查结束后，只做不影响功能的低风险优化。
- 最后跑完整 gate，只有全绿时才记录 `v1.3.0`。

## 具体步骤
1. 盘点 `git status`、现有 tag、最新 gate 状态，建立这轮计划。
2. 更新 `CHANGELOG.md` 和治理记录，提交并打 `v1.2.1` tag。
3. 并行审查：
   - 代码功能与稳定性
   - 文档准确性与摆放位置
   - 熵与维护链路状态
4. 汇总发现并执行低风险优化，必要时拆分模块、修正文档或收紧治理规则。
5. 跑 `doctor`、`entropy-check`、`harness-check`、`maintenance-check`、`pytest`。
6. 如果全部通过，更新 `CHANGELOG.md` 和治理记录，记录 `v1.3.0`。

## 发现与意外
- `v1.2.1` 备份点已经通过正式 tag 固定，但版本说明仍需在 tag 之后补一笔文档记录提交，避免移动 tag。
- `maintenance-check` 暴露出一条真实失配：`tests/test_pipeline.py` 中的周报链路测试没有同步 mock `analyze_report`，导致维护循环先于人工检查发现阻塞项。
- 文档主线整体正确，但入口文档仍有少量说明偏差和格式瑕疵，需要在不改功能的前提下顺手校正。
- 根文档和控制面对 provider 的表述发生过漂移：README 一度遗漏 `openrouter_api`，而 `chatgpt_web_manual` 同时被写成“常规 provider”和“独立人工工作流”。
- `docs_review` 之前只检查文档是否放对目录，没有检查 README / PROJECT_CONFIG 这种根文档的关键语义是否已经失真。

## 决策记录
- `v1.2.1` tag 保持指向 release commit，本轮后续的说明补充不回写到 tag。
- `features.weekly_report_enabled` 继续作为兼容保留字段处理；本轮不恢复它作为正式运行开关，而是以文档澄清和控制面收口为主。
- 大检查期间优先修真实阻塞项和低风险偏差，不引入新的结构性重构。
- 把 provider 常量统一抽到 `analysis_providers.py`，用小范围收口替代大规模重构，降低后续 README / UI / doctor 再次漂移的概率。
- 在 `docs_review` 中增加根文档契约检查，用 harness 直接卡住过时 provider 说明的回流。
